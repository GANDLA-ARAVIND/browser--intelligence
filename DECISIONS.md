# Decision log

The measurement record for [CLAUDE.md](CLAUDE.md). Every row here explains
**why** something is the way it is — what was measured, what was tried and
rejected, what a number actually came out at.

Rules that constrain future work do **not** live here; they are in CLAUDE.md
§14. The test for which file a row belongs in: does it tell a future
implementer what they *must do*, or does it explain *why* something is the way
it is? Must-do stays in CLAUDE.md, explains-why lives here.

**The §0 propagation rule spans both files.** When a row here corrects a
CLAUDE.md section, update that section in the same edit. A decision recorded
here while the spec section still says the old thing is exactly the drift this
split was made to prevent — the record grows monotonically, so an uncorrected
section stays wrong forever while looking authoritative.

Append new rows at the end. **Never rewrite a row to match a later finding that
changes its conclusion** — add a superseding row and say what it replaces, so
the reasoning stays auditable. Extending a row with further evidence for the
*same* conclusion is fine and preferred; that is accumulation, not revision.

| Decision | Rationale |
|---|---|
| No backend | Privacy is the differentiator; also removes cost and auth entirely |
| No vector DB | 15MB of vectors, measured 7.3ms brute-force scan at 10k — a DB is pure overhead |
| Derived taxonomy | A hand-written topic list only ever fits its author |
| No productivity score | Invented metrics are detectable and destroy trust in honest features |
| Extension page, not hosted dashboard | Same React work, zero server, privacy intact |
| Chromium-only v1 | ~75% of desktop users from one build; Firefox is 2–3% |
| Day boundary at 04:00 | Late-night work belongs to the previous day |
| Phase 0 clusters with mutual-kNN + shared-neighbour, not HDBSCAN | HDBSCAN needs a UMAP step to behave on 384 dims and has no trustworthy JS port; `--algo community` and `--algo kmeans` remain as comparison arms |
| Shared-neighbour test on every graph edge | Mutual-kNN alone chains: one accidental link welds two topics into one blob under connected components. Requiring shared context breaks bridges, which by definition have no mutual crowd |
| `scripts/export-history.mjs` reads Chrome's local SQLite | Takeout takes hours and drops `visitCount`; `node:sqlite` is built in, so this stays zero-dependency and fully local |
| Cluster output displays the original title, embeds the stripped one | react.dev titles every page "… – React", so the suffix stripper removes the one word that identifies the cluster. Measured: stripping costs 0.33 of within-group similarity and 63% of the topic/unrelated gap. Clustering still works; a human reading the output could not tell what the cluster was, which defeats the §11 exit criterion |
| **Encryption at rest downgraded, consciously — the threat model does not support it** | §9 originally required it; it was never built, and on inspection it should not be. The index sits in extension-local IndexedDB inside the Chrome profile directory, under the same OS permissions as Chrome's own `History` SQLite, saved passwords and session cookies. **An attacker who can read our store can already read all of those, every one of them higher-value.** Encrypting ours while they sit in plaintext beside it is security theatre. Worse, there is no key we can hold that such an attacker cannot: with no user passphrase in the product the key lives in `chrome.storage` — same profile, same permissions — so it is obfuscation, and shipping obfuscation *labelled* "encrypted" is worse than shipping nothing, because it invites trust it cannot earn. The controls that genuinely defend the user are already in §9 and are all pre-storage or user-driven: blocklist before extraction, pause, retroactive delete, separate Chrome profile. **v2 candidate:** a user-supplied passphrase is the one key an attacker with profile access lacks — but it changes the product, not the storage layer. A locked index cannot be searched, so it needs an unlock flow, a policy for capture while locked, and a forgotten-passphrase answer better than "your history is gone" |
| The quality verdict **controls** the extraction ladder; it does not annotate it | Recording quality and embedding the text anyway was the bug: Readability returned 519 chars of nav chrome and month names for a GitHub profile, scored it `poor`, and stored it regardless. A rung is now accepted the moment it is not `poor`, and the recorded tier is the one that actually **supplied** the text, not the last attempted. When every rung is poor the highest-scoring one wins rather than the last — the GitHub metadata description (0.54) beats its nav bar (0.14). Rungs are thunks so a rung never runs unless the ladder reaches it, which matters once step 2 adds tier-1 adapters that fetch transcripts |
| SPA navigation is detected by polling `location.href`, not by patching history | Most modern sites (YouTube, LinkedIn, Reddit, GitHub, Naukri) navigate via `pushState` with no document load, so load-time capture silently misses every page after the first — potentially a large fraction of browsing. Three options weighed: `chrome.webNavigation.onHistoryStateUpdated` is authoritative but costs a permission and a round trip; **monkey-patching `history.pushState` from a content script does not work at all**, because content scripts run in an isolated world with their own `history` binding and never see the page's calls — making it work needs a MAIN-world injection that many sites' CSP blocks. Polling won: the 1s dwell tick already exists, so it costs one string comparison, no permission, and no new failure mode, and it observes the *result* so it catches every navigation mechanism. Dwell resets on change, so 30s on video A cannot qualify video B. Fragment-only changes are ignored because `normalizeUrl` strips them anyway; `#/` routes are kept |
| **`coverage` measures completeness, not correctness** | A YouTube watch page scores good 0.91 at **100% coverage** — and the text is the video description plus the sidebar recommendation list. 100% means Readability extracted everything the page offered; it says nothing about whether the page offered the right thing. Coverage can only ever detect *under*-extraction. This is the failure class no structural threshold reaches, because the output is well-formed prose about the wrong subject, and it is the whole justification for the YouTube transcript adapter |
| A site named as needing an adapter on the evidence of one page was wrong | GitHub was listed for a tier-1 adapter after a *profile* page returned nav chrome and month names. Repo pages then measured good 0.87 / 7,412 chars / 82% coverage, and 7,998 chars of real README on another. Only profile and sub-tab pages fail, and the ladder already demotes those. The correction is cheap here; the general point is that one unrepresentative page is enough to justify building the wrong thing, and the adapter budget is 5–8 total (§8) |
| Text over ~115 units with zero sentence terminators is not prose | A structural fact about writing, not a tuned threshold: concatenated UI labels satisfy every other signal and produce not one terminator in 700 characters. Applied only where the script actually uses terminators, since Thai, Lao, Khmer and Myanmar do not. This is what finally catches the Naukri case independently of the stopword fix |
| Superseded — repeated UI labels defeat the stopword signal (fixed, see above) | A stored Naukri "Application History" capture (984 chars of `Recruiter Actions(0)Applies on Naukri(69)…Prep for this interviewSoftware EngineerPrep for this interview…`) re-scores **weak, 0.568** — not `poor`, so the ladder accepts it at tier 2 and embeds it. The stopword ratio came out **0.324, inside prose range**, because `"Prep for this interview"` repeated five times contributes *for* and *this* each time: repetition inflates the ratio without indicating prose. The signal that did fire was terminator density at **0.0**, but its 0.25 weight is not decisive. Candidate rule for later, deliberately not applied yet: 700+ characters with *zero* sentence terminators is structurally not prose regardless of other scores. Also open — whether `weak` should trigger fall-through when a lower rung scores better, not just `poor` |
| Extraction tier records method, not quality — they need separate fields | All six pages in the first capture test reported tier 2 (Readability), but a GitHub profile yielded 519 chars of nav chrome and month names, NeetCode yielded a 248-char announcement banner, and YouTube yielded the video description rather than the transcript. §8's coverage metric would have reported **100% success on a corpus where a third was unusable**. `extractionQuality` is now stored alongside the tier. Optional by design: backfilled pages had no extraction to assess |
| Structural quality signals catch non-prose, never wrong-prose | Measured on reconstructions of the six: **stopword ratio is the strongest discriminator** — nav chrome 0.08 against 0.38–0.63 for real prose — with absolute length catching the short banner. But the YouTube description scores 0.75 "good" and is still the wrong content, because it *is* prose. No structural metric will catch that; it needs a site adapter. Two traps found while building it: "mean words per sentence" runs **backwards** (text with no terminators becomes one enormous sentence, so a nav bar scored a perfect 1.0 — replaced with terminator density), and the English stopword list must be skipped entirely for non-Latin text rather than substituted with a neutral value, or every Telugu page scores as chrome |
| §5's "no vector DB" arithmetic holds, with margin | Brute-force top-20 cosine over normalized vectors, medians of three: **2,670 nodes 2.17ms · 5,747 nodes 4.51ms · 10,000 nodes 7.31ms · 50,000 nodes 33.7ms**. §5 predicted ~12ms at 10k, so the estimate was conservative by 1.6×. Linear in node count, as expected. At 50k it is still a third of a frame — a vector DB would remain pure overhead for years of browsing. Scanning collapsed representatives rather than all pages also stops twenty near-identical LeetCode rows filling the results |
| The width cap flipped the blocking ranking: collapse is now the dominant blocker | Post-fix medians in the extension: embed **96.4s** (was 133.8s), longest embed stall **1.3s** (was 17.1s), total **109.3s** (was 149.7s). Collapse now blocks **11.9s unbroken** against embed's 1.3s longest — the ranking inverted, exactly as the batch-size rule predicts: capping width shrank the per-batch unit of work while collapse remained a single synchronous pass over the whole corpus. Collapse is the Phase 3 responsiveness target |
| A stall offset is measured against the attributed *segment*, never a stage looked up by name | The dashboard reported "began −6ms into collapsing", which is impossible. A gap almost always straddles a boundary — the tick before a long block fires a few ms before the stage switches — and resolving the stage's start by *name* afterwards can return an earlier occurrence. `attribute()` now returns the winning segment's start alongside its label, and the offset is clamped at zero. Note the fix is in the offset, not the attribution: overlap already assigned the 11.9s block to collapse correctly, and reattributing it to the previous stage on the strength of a 6ms boundary artifact would have restored the exact misattribution bug fixed earlier |
| Batch cost is linear in padded sequence width, and one title can dominate a batch | Every title in a batch pads to the longest, so a single outlier taxes 31 others. Measured **Pearson r = 0.992** between padded width and batch duration (width² fits worse at 0.920, so FFN dominates attention at these lengths). Titles are median 10 tokens, p99 36 — but max 875, and that one batch cost 4.25s against a 0.142s median, **30×**. 34% of embed time was spent above median batch cost. This is the mirror image of the Phase 0 padding finding: equalising width bought no *accuracy*, but width is almost the whole *latency* story |
| Phase 0 baseline, superseded 2026-07-29: **91 clusters / 33.7% noise / 2,671 unique nodes / 5,818 kept** at `--knn 10 --shared 4` | Replaces 104 / 33.7% / 2,699 / 5,873. The corpus changed deliberately: the bare-URL junk rule drops 55 pages and the 64-token cap alters the vectors of the few very long titles. Noise held exactly at 33.7% and the recognisable clusters survived (DSA, job search, the GitHub portfolio), so this is corpus drift from an intended filter change, **not a regression**. Any future baseline comparison must start here |
| §3's context isolation is what keeps the UI alive — validated, not assumed | **87% of the run had a thread blocked, and the dashboard stayed fully responsive**, because every block was in the offscreen document while the dashboard ran in its own context. Had the pipeline lived in the dashboard, or in a worker sharing its thread, this would have been a two-minute UI freeze. The offscreen document is not merely "where the model fits" — it is the isolation boundary that makes a blocking pipeline tolerable at all. Keep heavy work out of the dashboard context permanently |
| The 253ms "model" stage is real, not a mislabel — but the 16.5s embed outlier is still unexplained | Suspected that ORT defers session init to first inference, which would hide the model cost inside the first embed batch. **Measured: it does not.** `pipeline()` takes 174ms and the first inference runs at 0.89× the median of the next five — no deferral, so 253ms in the extension is consistent with Node, not implausible. That leaves the 16.5s stall unaccounted for. `BlockingEvent` now records `sinceStageStartMs`: if the worst stall begins at ~0ms into embed it is lazy setup after all, and anywhere else it is not (GC, throttling, a pathological batch). Caveat: measured with `onnxruntime-node`, so confirm in the extension |
| WASM in the extension is ~3× slower than native ONNX in Node, as expected | Embed median 153.3s in the offscreen document against ~57s for the same corpus size in Node — single-threaded `ort-web` (forced by MV3's CSP, which blocks SharedArrayBuffer and blob workers) versus multi-threaded `onnxruntime-node`. Collapse is only 1.3–2.3× slower, which is the consistency check: it is pure JS on V8 in both, with no WASM involved |
| The model and the ONNX runtime ship inside the package; no `host_permissions` | A runtime download needs a host permission, which puts a second alarming line next to "read your browsing history", and a network call contradicts the pitch. `env.allowRemoteModels = false` makes it structural rather than aspirational: a missing file errors instead of silently fetching. Costs ~42MB packaged (22.6 model + 18.3 ORT wasm). Verified by loading with `fetch`, `http.request` and `https.request` all replaced by throwing stubs |
| `content_security_policy.extension_pages` declares `'wasm-unsafe-eval'` | MV3 blocks `WebAssembly.instantiate` outright without it, so the ONNX runtime cannot start. It permits WASM compiled from bytes already in the package — it is *not* remote code, does not relax `script-src` for JavaScript, and leaves the no-network guarantee intact. Manifest keys carry no comment: JSON has none, and Chrome logs `//`-prefixed keys as errors |
| WASM streaming compilation is unavailable in MV3; the ArrayBuffer fallback is accepted | `WebAssembly.instantiateStreaming` needs `Content-Type: application/wasm`, and nothing controls the response headers for a `chrome-extension://` resource — there is no server config to set. onnxruntime-web 1.14 exposes no `wasmBinary` hook to bypass it either, so the emscripten fallback is the only path. Measured cost: read 8ms + compile 18ms = 26ms, of which streaming would have hidden at most the 8ms read, once per offscreen document. Do not re-investigate |
| Audit of remaining absolute similarity constants | `--min-sim` 0.20 (inert, above); `--threshold` 0.35 (`--algo community` only, a comparison arm); `--dup-threshold` 0.97 (**defensible** — it detects near-*identity*, not topical relatedness: duplicates sit at ~1.0 against a measured cross-topic max of 0.44, so the margin is enormous and scale-stable). §5's 0.40 zero-shot threshold remains unverified. Frequency rules are already scale-relative (`max(5, 0.3%)`) and need no change |
| Junk titles (auth walls, bot checks, error pages) are dropped before embedding | They carry no topic, recur in the hundreds under many distinct URLs so the normalized-URL dedupe never sees them, and once embedded they form dense identical neighbourhoods. Most are auth pages that §9 forbids capturing at all |
| Junk prefix patterns apply only to titles under 40 chars | An interstitial announces itself in a few words. `/^error/` alone eats "Error handling with Result and the question mark operator", a real Rust doc page — length is what separates the two |
| Near-duplicate pages collapse to one weighted node before clustering | LeetCode serves `/problems/two-sum/`, `/description/` and `/submissions/` under one title, so URL dedupe misses them. Twenty copies saturate a page's k nearest neighbours with itself: no related page can link, every problem becomes its own cluster, and unique pages get no mutual edges at all. Measured on real history: 553 clusters, 41% noise, four separate "Sign in" clusters |
| int8 batch-shape drift accepted, not engineered around | A title's vector shifts ~0.993 cosine when its batch has a different padded sequence width. fp32 shows none, so mean pooling masks padding correctly. Padding short batches to 32 rows does not help — width, not row count, is the driver — and top-6 neighbour rank is 100% stable across regroupings, so nothing mutual-kNN reads is affected |
| **Generalises the `coverage` row above: structural quality cannot detect wrong-*topic* prose, and boilerplate is the common case** | The YouTube row framed this as a transcript-vs-description problem. Real captures show it is the whole class, and far more frequent: "Privacy Notice" scored **good 0.90** (a cookie policy), "Search & Apply" **0.95 at 15% coverage** (privacy-policy text), "Work with Concentrix" **0.67** (a recruitment-fraud warning). Legal boilerplate is *perfect* prose — full sentences, high stopword ratio, correct terminators — so it scores at the top of the scale while carrying nothing about what the user was doing. Every structural signal we have measures "is this well-formed text", and boilerplate answers yes. **A high score at low coverage is the tell**: 0.95 at 15% means high confidence in a *fragment* of the page, which is close to the opposite of what a quality score should imply. Open question, not yet decided: should coverage cap the score, so a fragment cannot score above what its share of the page justifies? **The class also includes prose-shaped UI chrome**, not only legal boilerplate: a GitHub dashboard scored **good 0.73** on "Skip to content Dashboard Provide feedback Saved searches Use saved searches to filter your results more quickly…". Help text is written in grammatical sentences, so every structural signal reports prose. This is a **new** failure rather than a survival of the old one — it passes on genuine sentence structure, not on repetition, so the unique-token stopword fix has no purchase on it and could not have caught it. **Phase 3 concern** — these pages will cluster, and a "privacy policy" cluster spanning twenty unrelated employers, or a "dashboard chrome" cluster spanning every SaaS tool, pollutes the taxonomy while looking legitimate |
| Job portals reuse one title across unrelated pages | Two captures both titled "Cognizant Career Portal": one 3,970 chars of a Python/Snowflake job description, one 167 chars of a disability disclosure form. The captured vectors separate them correctly because they are built from body text — but the *backfilled* versions of these same pages carry only the ambiguous shared title, so they are indistinguishable in the index. This is a concrete instance of the heterogeneity problem: the same URL space is well-separated when captured and collapsed-together when backfilled, which is exactly the ingestion-route bias to quantify in the Phase 2 step 2 measurement |
| The dwell gate leaked through a throttled timer — reproduced, fixed | Reported as "captured at 25s active, below the 30s threshold". **The report was two separate things.** The 25s is *correct*: `activeSeconds` and dwell are different numbers, and a page loaded in a background tab has a stale input window, so the first seconds of focused-but-untouched reading legitimately do not count as active. Reproduced exactly — dwell 30,000ms with activeSeconds 25 — and §9 is working as written. **A real leak was found while looking**, though not the reported one: `elapsed` is wall time since the previous tick, and Chrome throttles `setInterval` in a hidden tab to ~once a minute, so the first tick after refocusing credited the whole gap as focused time. Measured: one tick turned ~0.5s of real attention into 60,000ms of dwell and tripped the gate instantly. Fixed by resetting the elapsed clock on every visibility/focus transition and clamping `elapsed` to 1.5 ticks — the same case now yields 500ms and does not capture. A hard assertion at the capture path re-checks the threshold, because this class of leak is silent: the page is simply indexed on attention it never received |
| Adapters named from a single observed failure keep turning out unnecessary — that is now a pattern, not a coincidence | **GitHub** was listed after one profile page returned nav chrome; repo pages then measured good 0.87 at 82% coverage and it was removed. **NeetCode** is now the second candidate: "Reverse Nodes in K-Group" captured at **tier 3, good 0.74, 347 chars**, and the text is the actual problem statement, lifted from the meta description — the ladder handled it without an adapter, which is exactly what §8 says tier 3 is for. Both were named from one page each, before the quality-driven fall-through existed. The lesson is not "stop proposing adapters" but **the ladder must be working before the adapter list means anything**: a rung that silently accepts poor output makes every site look like it needs a bespoke extractor. Still on the §11 list pending 3–4 more NeetCode problems, as one good capture is the same evidence that produced the GitHub mistake |
| Window blur does not leak dwell, but the fix for the throttled-tick leak did | Checked because `visibilitychange` never fires when the whole Chrome window loses focus to another application — the tab stays `visible`. No leak: `isFocused()` also requires `document.hasFocus()`, which goes false in that case, so switching to an editor stops dwell accrual. **A real defect turned up in the fix from the previous session, though.** Its focus/blur listeners used `{ capture: true }`; element `focus`/`blur` do not bubble, but a capture-phase *window* listener still sees them, so every click into a text field reset the elapsed clock and truncated that interval. Measured on a form-heavy page: **22% of dwell lost, and the 30s gate reached 25 seconds late.** Now registered without `capture`, with `visibilitychange` on the document where it actually fires. **The direction is the important part.** It under-counted, so it *suppressed* captures rather than leaking them — and suppression is symptomless: a page that was never captured is indistinguishable from a page that was never visited. Nothing in the corpus, the counts or the dashboard would ever have shown it. The leaking twin of this bug (the throttled tick) was found within one session because it produced a visibly wrong record; this one survived review and shipped. Recorded as a binding rule in CLAUDE.md §14: gates must be tested in both directions |
| A per-page `activeSeconds` filter is the wrong way to exclude passive media, and is the obvious thing to build | Option (c) — capture everything, defer to Phase 3 — was chosen for passive consumption, and the near-miss was recommending `activeSeconds` as the per-page test to go with it. **It does not discriminate.** §9 counts a second as active only if there was input within the previous 60s, so a 40-minute conference talk watched attentively, without touching anything, lands at `activeSeconds` ~0 — identical to an hour of YouTube autoplay. A per-page filter therefore drops precisely the case that made the stricter gating options unacceptable in the first place: real, deliberate, valuable viewing. The discriminator is the **session shape**, not the page: many sequential pages on one domain, all at ~0 active, each short. One long page at ~0 active is attention; twenty short ones in a row are autoplay. Written into §11 Phase 3 as a requirement rather than left as a note, because "Phase 3 filters on activeSeconds" is what gets implemented otherwise — it is the shortest path from the stored field to a filter, and it is wrong |
